01신제품 기회 보고서

Step 1 · Identify Opportunities — 1페이지 보고서 양식(제목/설명/스케치)

Title

Pressure Valve — 영어 표현으로 하루의 스트레스를 짧게 배출하는 벤팅 툴

Description — What / Who / Why

What. 카테고리를 고르거나 오늘 있었던 일을 한 줄 쓰면, 순한맛/매운맛 강도로 조절된 영어 표현과 한국어 뉘앙스를 즉시 보여주는 인터랙티브 웹 앱.

Who. 영어 학습에 대한 부담은 크지만 스트레스는 매일 쌓이는 20~30대 직장인·학생 — "배우기"보다 "풀기"가 목적인 사용자.

Why (가치 가설). 기존 영어 회화 앱(예: 영트임류)은 학습에 초점이 맞춰져 있고, 감정 배출용 콘텐츠는 별도 시장이 없다. "확실히 존재하는 스트레스 해소 니즈"에 "영어 표현"이라는 실용적 가치를 얹으면, 학습 부담 없이도 매일 열어보고 싶은 도구가 될 수 있다.

Sketch

이미 프로토타입 v1~v3까지 제작·배포 완료 — 카테고리 선택, 강도 토글, 발음 듣기, 즐겨찾기 기능 포함.

이번에 드러난 건 사실 두 단계의 문제였습니다. ① 어떤 카테고리로 갈지(work/people/...) ② 그 카테고리 안에서 어떤 영어 문장을 보여줄지. 위 문장은 "상사"가 있어 카테고리는 work로 정확히 갔지만, work 안에서는 무작위로 문장을 고르다 보니 "마감 때문에 힘들다"는 전혀 다른 뉘앙스의 문장이 나온 것이었습니다.

이건 코드 문제가 아니라 기기의 텍스트 음성 변환(TTS) 엔진 설정 문제일 가능성이 커요. 안드로이드는 브라우저가 자체적으로 소리를 내는 게 아니라 시스템 TTS 엔진(삼성 또는 구글)에 요청을 보내는 구조라서, 그 엔진에 영어 음성 데이터가 없으면 브라우저 입장에선 "정상적으로 요청은 보냈는데 조용히 아무 일도 안 일어나는" 상태가 됩니다. 지난 코드 수정으로 실패 시 버튼이 빨갛게 흔들리는 시각 피드백을 추가했으니, 그게 뜨는지 여부로 원인을 좁힐 수 있어요.

왜 바꿨는가

섹션 26에서 정직하게 남겨뒀던 한계 — "카테고리는 맞아도 카테고리 안 문장 선택은 여전히 랜덤이라 정확히 그 상황에 맞는 한 문장까진 못 맞춘다" — 는 사실 자유 서술형 입력을 유지하는 한 구조적으로 풀기 어려운 문제였습니다. 키워드를 아무리 늘려도 문장 단위 정확도까지 올리려면 결국 사용자가 쓸 수 있는 모든 표현을 예측해서 키워드화해야 하는데, 이건 서버 없는 클라이언트 앱에서 한계가 뚜렷합니다. 사용자가 제안한 방향은 이 문제를 추론이 아니라 선택으로 바꾸는 것이었고, 이렇게 하면 매칭 정확도가 "확률적으로 개선"이 아니라 설계상 100%가 됩니다.

무엇을 바꿨는가

자유 서술형 입력창(텍스트박스 + "표현 만들기"/"지우기" 버튼)과 그 뒤의 2단계 키워드 매칭 로직(문장 → 카테고리 점수 계산 → 카테고리 내 랜덤 문장)을 완전히 제거했습니다. 그 자리에 5개 카테고리별로 묶인 18개의 구체적 상황 칩을 배치했고, 각 칩은 미리 정해진 순한맛 1문장 + 매운맛 1문장에 정확히 1:1로 연결됩니다. 칩을 누르면 추론 없이 바로 그 문장이 뜨고, 강도 토글(순한맛/매운맛)에 따라 같은 상황이라도 다른 문장이 나옵니다.

경계 원칙 정리 — 직장·업무 vs 사람·관계

사용자가 스스로도 헷갈려 한 두 지점(직장 위계가 사람 문제인지 업무 문제인지, 손님·거래처가 어느 쪽인지)을 계기로 기준을 하나로 정리했습니다: "무엇 때문에" 힘든가는 직장·업무, "누구 때문에" 힘든가는 사람·관계. 이 기준으로 손님·거래처 담당자의 무리한 요구·무례함은 사람·관계로, 학교 선후배·동기는 (영어 표현 패턴이 직장 위계와 거의 같아서) 직장 상사·후임과 하나의 "위계 관계" 묶음으로 합쳤습니다. 두 결정 모두 사용자 확인을 받았습니다.

구조 변경 — 1단계 탭은 그대로, 사람·관계 안에만 하위그룹 추가

칩을 누르면 바로 문장이 뜨는 1탭 구조(추가 선택 단계 없음)는 그대로 유지했습니다. 대신 사람·관계 섹션 안에서만 관계 유형별로 얇은 하위그룹 라벨(왼쪽 세로선 + 작은 글씨)을 넣어 시각적으로만 묶었습니다 — 다른 4개 카테고리(직장·업무, 소소한 빡침, 자책·실수, 그냥 다 지침)는 하위그룹이 없을 때와 동일하게 평평한 칩 목록으로 렌더링되도록 렌더 함수를 조건 분기했습니다.

30UX 정리 · 컬러 리디자인 — 1·2번 중복 제거, 다크 모드 재조정

계기 — "1번과 2번 내용이 중복되는거같아, 1번에서 선택하면 하위내용으로 떠야할거같은데" · "카테고리 글씨크기가 너무 작고 눈에띄지 않아" · "앱 사이트 전체적으로 너무 어두워"

문제 1 — 밸브(1번)와 상황 목록(2번)이 같은 카테고리를 두 번 보여줌

기존에는 1번(밸브 5개)과 2번(상황 리스트) 둘 다 5개 카테고리(직장·업무/사람·관계/소소한 빡침/자책·실수/그냥 다 지침) 이름을 각자 따로 표시하고 있었고, 2번은 밸브 선택과 무관하게 항상 5개 카테고리 전부를 한 화면에 펼쳐두고 있어서 정보가 중복되고 화면이 길고 산만했습니다.

조치 — 1번이 2번의 필터가 되도록 연결

2번을 "선택 전엔 안내 문구만, 밸브를 고르면 그 카테고리 상황만" 뜨는 구조로 바꿨습니다. 밸브를 누르면 ① 기존처럼 즉시 랜덤 문장이 뜨고, ② 동시에 2번 영역이 그 카테고리 이름을 큰 제목으로 보여주며 해당 상황 칩만 필터링해서 표시합니다. 다른 밸브를 누르면 2번 내용이 통째로 그 카테고리로 교체됩니다 — 5개를 다 보여주던 걸 1개만 보여주는 것으로 바꾼 것뿐이라 코드 복잡도는 오히려 줄었습니다(항상 5번 반복하던 렌더링 루프를 1번만 도는 함수로 교체).

문제 2 — 카테고리·하위그룹 글씨가 작고 안 보임

이제 2번에는 카테고리 이름이 화면에 한 번만(선택된 것만) 뜨기 때문에, 그 자리를 작은 모노스페이스 라벨(10.5px, 저채도 회색)에서 큰 제목(21px, 굵게, 브랜드 색상 ember, 점 아이콘 포함)으로 격상시켰습니다. 사람·관계 안의 하위그룹 라벨(친구·애인 등)도 11.5px 저채도에서 14px, 진한 잉크색, 굵게로 올리고 왼쪽에 색이 있는 세로선을 추가해 구획을 눈에 띄게 했습니다.

문제 3 — 전체적으로 너무 어둡다 → 다크 모드 톤 재조정

기기가 다크 모드일 때 배경이 거의 검정에 가까운 톤(#161310, 명도 매우 낮음)이라 무겁고 답답하게 느껴졌던 것으로 보입니다. "화날 때 어두운 게 나은가?"라는 질문에 대한 판단은: 어두운 화면 자체가 문제가 아니라, 지나치게 어둡고 채도가 낮아 눌리는 느낌이 문제라고 봤습니다. 그래서 다크 모드를 없애지 않고, 같은 ember(주황빛 잉걸불) 색 계열 안에서 배경 명도를 확 끌어올리고(거의 검정 → 따뜻한 짙은 갈색, 배경색 RGB 기준 약 2배 밝게) 강조색(ember)과 완화색(relief 민트)의 채도·밝기를 높여 "불씨가 살아있는" 느낌으로 바꿨습니다. 라이트 모드도 배경을 더 밝고 따뜻하게(크림→살짝 더 밝은 톤), 카드 배경을 순백으로 올려 대비를 또렷하게 했습니다. 헤더 위쪽에는 은은한 ember 색 방사형 글로우를 하나 추가해 "불이 지펴지는" 느낌의 포인트를 줬습니다(과하지 않게 한 곳에만).

색상 대비(WCAG 명암비)도 계산해 확인했습니다: 본문 텍스트(ink) 대 배경 — 라이트 14.7:1, 다크 14.6:1(둘 다 최상급) · 보조 텍스트(ink-soft) — 라이트 5.4:1, 다크 8.0:1(AA 통과, 다크는 기존보다 legibility 크게 개선) · 강조색(ember) 큰 글씨 기준 — 라이트 3.5:1, 다크 6.3:1(WCAG 큰 글씨 기준 3:1 이상 통과, 다크 모드는 기존 5.99:1보다도 개선).

디버깅 — 재구조화 후 전체 재검증

Playwright로 검증: 초기 화면엔 안내 문구만 뜨고 상황 칩은 0개(정상) · 밸브 클릭 시 안내 문구가 사라지고 해당 카테고리 상황만 뜨는지(사람·관계 16개+하위그룹 6개, 직장·업무 6개+하위그룹 0개 등) 확인 · 다른 밸브로 바꾸면 내용이 전부 교체되는지 확인 · 상황 칩 선택·"다른 표현"·즐겨찾기 모두 정상 동작 · 라이트/다크 모드 각각에서 배경색이 의도한 값으로 렌더링되는지 확인(다크 배경 RGB(44,28,17) — 기존 RGB(22,19,16) 대비 확연히 밝아짐) · 다크 모드에서 5개 카테고리를 전부 돌며 38개 상황 전체 재클릭, 정확한 문장 노출 확인(불일치 0건) · 콘솔 에러 0건. 구현 중 새로 추가한 헤더 글로우 장식 요소가 390px/320px에서 가로 스크롤을 유발하는 회귀가 있었는데(장식 요소 너비가 좁은 화면보다 넓어서 발생), 글로우 너비를 뷰포트에 비례하도록 고치고 overflow-x: hidden 안전장치를 추가해 해결하고 재검증했습니다.

색상 되돌림 — "배경이 오히려 화를 돋운다"

색 변경 직후 사용자 피드백: 새 다크 모드 배경(따뜻한 갈색 톤)이 오히려 보기 불편하고 거슬린다는 반응. "디자인은 나중에, 지금은 기능부터"라는 방향 정리에 따라 라이트·다크 모드 색상 토큰 전체와 헤더 글로우 장식을 이번 변경 직전 상태로 완전히 되돌렸습니다(다크 배경 다시 #161310). 1번→2번 필터링 연결, 큰 글씨 카테고리 제목, 하위그룹 라벨 확대 등 기능·가독성 개선분은 색과 무관하므로 그대로 유지했습니다. 되돌린 뒤 Playwright로 라이트/다크 배경색이 정확히 예전 값으로 복원됐는지, 1번→2번 필터링이 여전히 정상 동작하는지, 콘솔 에러가 없는지 재확인했습니다. 색상·룩앤필 관련 작업은 사용자 요청이 있을 때까지 보류합니다.

31디버깅 로그 — "다른 표현" 선택 해제 · TTS 신뢰성 개선

사용자 리포트 — "1번 누르고 2번 누르고 나서 다른표현 누르면 2번 누른게 다시 클릭해제되는 상황이 뜨네" + "스피커로 음성지원되게끔 해줄래?"

1. "다른 표현" 클릭 시 상황 칩 선택 해제 — 의도 변경

원래는 "다른 표현"을 누르면 그 순간 정확한 매칭이 아닌 카테고리 내 랜덤 문장으로 바뀌는 것이므로, 방금 고른 상황 칩의 활성 표시를 의도적으로 지웠습니다(그 칩의 정확한 문장이 더 이상 화면에 없다는 걸 알리려는 의도). 하지만 사용자 입장에서는 방금 고른 게 취소된 것처럼 보여 거슬린다는 피드백을 받아, "다른 표현" 클릭 시 칩 선택 표시를 그대로 유지하도록 바꿨습니다. 카테고리(밸브)를 바꾸면 상황 목록 자체가 통째로 새로 그려지므로 그때는 여전히 선택이 해제됩니다(다른 카테고리의 칩이라 당연히 해제되어야 함) — 이 부분은 그대로 뒀습니다.

2. TTS(음성 지원) 신뢰성 개선

이전 갤럭시 S23+ 무음 리포트를 다시 들여다보고, 코드 레벨에서 고칠 수 있는 두 가지 알려진 버그 패턴을 찾아 고쳤습니다. ① 목소리 목록 지연 로딩 문제 — 안드로이드 Chrome·삼성 인터넷 등 다수 브라우저는 페이지 로드 직후 getVoices()를 부르면 빈 배열을 주고, 실제 목소리 목록은 비동기로 나중에 준비되어 voiceschanged 이벤트로 알려줍니다. 기존 코드는 스피커 버튼을 누른 "그 순간"에만 목소리를 조회해서, 영어 목소리가 실제로 설치돼 있어도 타이밍이 안 맞으면 못 찾고 기본 목소리로 새는 경우가 있었습니다 — 페이지 로드 시점부터 목소리 목록을 미리 캐시해두고 이벤트로 계속 갱신하도록 고쳤습니다. ② 큐가 멈춰버리는(paused) 크롬 계열 알려진 버그 — 특정 상황에서 speechSynthesis 큐가 내부적으로 멈춘 채로 남아 speak()을 불러도 조용히 아무 일도 안 일어나는 문제가 문서화되어 있어, 발화 직전에 항상 resume()을 먼저 호출하도록 방어 코드를 추가했습니다(정상 상태에서는 아무 영향 없음).

이번에도 밝혀둘 한계. 이 샌드박스 환경엔 실제 스피커·TTS 엔진이 없어서(getVoices()가 항상 빈 배열, speak()은 항상 synthesis-failed 에러) 실제 소리가 나는지는 여전히 이 환경에서 검증할 수 없습니다. 코드가 에러 없이 정상 흐름을 타는지, 실패 시 빨간 흔들림 피드백이 여전히 정확히 뜨는지는 Playwright로 확인했습니다. 두 개선 모두 기기에 영어 음성 데이터가 아예 없는 경우까지 고칠 수는 없고(그건 여전히 기기 설정 문제), 실제로 개선되는지는 갤럭시 S23+ 같은 실기기에서 직접 확인이 필요합니다.
